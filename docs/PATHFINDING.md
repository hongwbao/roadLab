# 当前寻路逻辑与规模扩展

当前是独立实现的车道级 Dijkstra、IDM 跟车和 MOBIL 思路的换道决策。原型仍在浏览器主线程运行，车辆上限为 350，尚未验证上万辆车。这里描述实际代码，并将未来方案与已经实现的部分分开。

## 从道路到路线

1. **重建道路图。** 道路编辑后调用 `Simulation.configure()`，缓存路段弧长、路口裁切范围和几何连接。配置时检查入口与出口组合是否可达。
2. **建立搜索状态。** 一个状态为“道路 ID＋方向＋入口车道”。合法连接决定可以从哪条出口车道进入下一段道路的哪条车道。
3. **检查变道可行性。** 从入口车道变到出口车道时，检查方向、沿线车道宽度以及道路内实际可用距离。每跨一条车道按至少 20 米规划，并保留 6 米余量；路口内部裁切掉的距离不算变道空间。这里是寻路的保守可行性估计，实际低速变道轨迹可以更短。
4. **计算路径成本。** 自由流时间为路段剩余长度除以限速；每跨一条车道增加约 2.5 秒代价，并计入车道何时变宽可用。转弯、横向错位及拥堵增加成本。
5. **累计成本最小。** Dijkstra 在可达状态中选出总成本最低的路径。当前从开放集合中线性寻找最低成本状态，尚未改为优先队列或 A*。
6. **保存执行计划。** 每段路线保存道路、方向、入口车道和出口车道，车辆沿计划行驶；运动更新不重新搜索整张路网。

拥堵成本取该路段入口车道与必须使用的出口车道两者中的较大值。这样不能通过“先选空车道，最后插入长队”把必经队列从路径成本中抹掉。入口随机车道偏好仅作为很小的平局偏好，转弯车辆优先在合适车道生成；已经在路上的车辆重规划时仍固定从实际车道出发。

## 计算何时发生

| 工作           | 当前触发方式                                                                    |
| -------------- | ------------------------------------------------------------------------------- |
| 拓扑和静态几何 | 道路编辑或地图载入后重建                                                        |
| 发车及初始路线 | 以 0.2 模拟秒为需求处理间隔，有安全入口空间才生成车辆                           |
| 拥堵统计       | 每秒采样，使用 80% 旧值＋20% 新值平滑，延误估计上限 90 秒                       |
| 自主换道       | 约每 0.45–0.57 秒决策一次，变道完成后自主换道冷却 2.5 秒                        |
| 重新寻路       | 当前或前方道路拥堵、长期停滞等情况下尝试；未改道至少间隔 5 秒，成功后冷却 10 秒 |
| 跟车及位置     | 随模拟更新积分，每个积分步不超过 0.025 秒                                       |
| 渲染           | Three.js 使用车辆位置、朝向和俯仰更新实例化网格                                 |

新路线通常至少节省 2.5 秒且改善 15% 才采用，避免稍有波动就反复改道。错过可完成的出口变道位置时，可以尝试可行替代路线。

## 寻路与路口准入的区别

寻路回答“从哪里到哪里、经过哪些车道”，局部驾驶回答“这一刻能往前开多少”。两者互相影响，但不是同一项计算。

当前无信号路口按用户确定的阶段规则：**只检查出口目标车道是否有接收车辆的空间，不因横向车流或转向路径占用提前让行。** 同一路径车辆按曲线行驶距离正常跟车。准入检查与驾驶预判共用 80 米范围，不把尚未检查当作禁止通行；跨道路和连接曲线时继续使用积分剩余距离，避免边界顿挫。实际车身矩形检测独立保留以避免穿模，因此大流量下仍可能在路口内拥堵或僵持。红绿灯及其路权控制尚未实现。

## 《天际线 2》公开确认了什么

官方说明将沿途跟车、换道等局部决策与路线决策区分开，路径成本包含时间、舒适、金钱和行为因素；寻路与模拟利用多核 CPU，规模仍受硬件限制。[官方 Traffic AI 介绍](https://www.paradoxinteractive.com/games/cities-skylines-ii/features/traffic-ai)

官方还确认游戏使用 Unity ECS 和 Burst 来利用多线程与底层优化。Burst 能把兼容的 C# 代码编译成优化的原生 CPU 代码。[官方代码 Mod 技术介绍](https://www.paradoxinteractive.com/games/cities-skylines-ii/modding/dev-diary-3-code-modding)、[Unity Burst 文档](https://docs.unity3d.com/Packages/com.unity.burst@1.8/manual/index.html)

这些资料没有给出完整寻路源代码，不能据此断言游戏的具体搜索器、分层图或路线缓存策略。

## 我们如何扩展到更多车辆

并发车辆数量不等于每帧寻路次数。作为算术示例，一万辆车、平均行程 600 秒，在稳定且均匀出行时约每秒产生 17 条新路线；如果让所有车辆每 5 秒重算一次，就会达到每秒 2,000 次。突发出行和改道还会增加峰值请求，需要排队和计算预算。

以下是后续方案，目前尚未全部实现：

- **减少搜索工作：** 将开放集合改为优先队列；需要时使用可采纳的启发式改为 A*；大地图再考虑道路级走廊与局部车道级搜索。
- **控制请求峰值：** 路线请求排队、分帧限额；道路版本及拥堵版本变化后按范围失效缓存，避免全城同时重算。
- **缩小局部查询：** 按车道和空间单元查前后车及近邻，避免每辆车扫描所有车辆。当前已实现车道快照和碰撞空间索引，部分换道扫描仍有继续优化空间。
- **改进数据布局：** 位置、速度和车道使用连续数组，减少对象分配、随机访存及垃圾回收。
- **移出主线程：** 使用 Web Worker 执行模拟与寻路，主线程消费结果并绘制；根据测量结果决定是否将热点改为 C++/WASM。
- **分开更新频率：** 全局路线、换道、跟车和渲染采用适合各自工作的频率，渲染可插值；积分和碰撞精度需要单独验证。

这些是本项目的扩展路线，不是对《天际线》未公开实现的推断，也不是已经达到一万辆车的性能承诺。
